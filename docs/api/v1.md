# MaterialLedger HTTP API v1

## Scope and authentication

The v1 API base path is `/api/v1`. It is an authenticated JSON API that uses the **same ASP.NET Core cookie session as the MaterialLedger web UI**. This version does not accept bearer tokens and does not provide a token-issuance endpoint. API clients must establish a supported UI login session and send its cookie. Clients should use HTTPS to protect session credentials in transit.

All API routes require an authenticated user. Read routes and attachment downloads allow every authenticated role. `POST /commands` and attachment uploads require the `Programmer` or `Manager` role; an authenticated `Operator` receives `403`.

The API uses camel-case JSON properties. Enum values are JSON strings and use the exact .NET enum spelling shown below (for example, `FullSheetBundle` and `purchase-order` are deliberately different):

| Enum | Accepted/returned values |
|---|---|
| `InventoryItemKind` | `FullSheetBundle`, `FullSheet`, `Drop` |
| `InventoryItemStatus` | `Available`, `Reserved`, `AwaitingCloseout`, `Quarantined`, `Depleted`, `Scrapped` |
| `ShapeClassification` | `Rectangular`, `IrregularConservativeRectangle`, `Unknown` |
| `ReservationEquipment` | `Laser`, `Plasma`, `Shear`, `Other` |
| `ReservationStatus` | `Proposed`, `Approved`, `Released`, `AwaitingCloseout`, `ClosedConsumed`, `ClosedReturned`, `Cancelled`, `Exception` |
| `ExpectedRemainderSource` | `OpenNest`, `Manual` |
| `InventoryLocationType` | `Area`, `Rack`, `Shelf`, `Bay`, `Staging`, `Quarantine`, `Scrap` |
| `InventoryStorageMode` | `RolloutShelf`, `VerticalDropBay`, `FloorStaging`, `Other` |
| attachment route `entityType` | `inventory-item`, `material-reservation`, `material-transaction`, `material-exception`, `purchase-order` |

The API returns explicit DTOs, never EF entities. It does not return password hashes, normalized keys, row versions, operation-log request/result payloads, or filesystem storage paths.

## Read routes

All read routes return `200 OK` with JSON unless stated otherwise.

### `GET /api/v1/materials`

Returns active material specifications in the deterministic catalog order used by `MaterialSpecService.SearchAsync`.

- Optional query: `q` — material search text.
- Each result has `id`, `materialFamily`, `grade`, `finish`, `thicknessIn`, `displayName`, and `gaugeLabel`.

### `GET /api/v1/inventory`

Returns inventory availability summaries. The optional query parameters mirror the inventory filter:

| Query | Type | Notes |
|---|---|---|
| `materialFamily` | string | Exact/filter service material family value |
| `grade` | string | Material grade |
| `finish` | string | Material finish |
| `thicknessIn` | decimal | Thickness in inches |
| `itemKind` | `InventoryItemKind` | Enum spelling above |
| `minUsableWidthIn` | decimal | Minimum usable width in inches |
| `minUsableLengthIn` | decimal | Minimum usable length in inches |
| `locationCode` | string | Location code |
| `availableOnly` | boolean | Defaults to `true` when omitted |

Each summary has `id`, `publicItemCode`, `materialSpecDisplayName`, `materialDescription`, `thicknessIn`, `gaugeLabel`, `itemKind`, `status`, `quantityOnHand`, `availableQuantity`, `usableWidthIn`, `usableLengthIn`, `locationCode`, `lastObservedAtUtc`, `lastObservedByDisplayName`, and `isStale`.

There is no page-number/page-size pagination parameter in v1; a filtered inventory request returns the complete matching result set. Clients should constrain results with the filter parameters and must not assume an implicit page size.

### `GET /api/v1/inventory/{id}`

Returns the same canonical availability summary for an inventory item. For a `Drop`, the response additionally has `sourceSheet`, containing the source item summary; non-drop responses do not include that property. A missing item returns the standard `404` problem.

### `GET /api/v1/locations`

Returns active locations ordered by `sortOrder`, then `locationCode`. Each result has `id`, `parentId`, `parentCode`, `code`, `displayName`, `type`, `storageMode`, `capacityConfirmed`, and `notes`.

### `GET /api/v1/reservations/{id}`

Returns a reservation DTO with `materialReservationId`, `inventoryItemId`, `status`, `equipment`, `shopOpsJobId`, `drawingId`, `drawingRevision`, `pepNestYear`, `pepNestName`, `openNestNestId`, `nestName`, `laserProgramRecordId`, and `createdAtUtc`. A missing reservation returns `404`.

`openNestNestId` (UUID or `null`) is the OpenNest.Server nest the hold was created for, and `nestName` is the nest name captured when the hold was created. `pepNestYear` and `pepNestName` are **deprecated**: they are only set on holds created against a PEP nest and will be removed when PEP is retired. A hold carries either the OpenNest pair or the PEP pair, never both.

## Commands

`POST /api/v1/commands` is the only v1 command route. It requires `Programmer` or `Manager` and a single `Idempotency-Key` request header containing a UUID/GUID. The header must be present exactly once; missing, blank, duplicate, or malformed values return a `400` validation problem before any command is dispatched.

The key is passed to the existing operation log as its `CorrelationId`; it is **not** a separate idempotency implementation. The existing operation-log scope is global: do not reuse a key for another command, user, or semantically changed request. A key reused with a different command kind or canonical typed payload returns `409` `idempotency-conflict`. A key owned by a different user returns `403` `idempotency-key-ownership` and never reveals a replay result. Optional values should be sent consistently (`null` or omitted consistently), and expected remnants retain caller-supplied order; use a new key when changing a request.

A first successful command returns `201 Created`, a `Location` header for its created resource, and an envelope:

```json
{ "kind": "receive-material", "result": { "inventoryItemId": 456, "sheetLotId": 78, "publicItemCode": "SHEET-456" } }
```

A successful identical replay returns `200 OK`, the identical envelope, and `Idempotent-Replay: true`. The server derives replay metadata from the operation log; clients must not infer replay by searching for side effects.

### `kind: "receive-material"`

Supply `kind` and exactly one `receiveMaterial` object. Required fields are `inventoryLocationId`, `materialSpecId`, `itemKind`, `quantity`, `shapeClassification`, `isQuarantined`, and nonblank `purchaseOrderNumber`. `quantity` is a whole number of at least one, and `Drop` is not valid for this command.

`vendorId` and `vendorPartId` are optional numeric reference IDs. For a direct receipt, a supplied part must belong to the supplied active vendor; the server derives the immutable vendor and part snapshot strings. For a receipt against `purchaseOrderLineId`, the server derives references and snapshot strings from the PO header and line; supplied IDs, when present, must agree. `vendorName` and `vendorPartNumber` are not accepted as identity inputs.

```json
{
  "kind": "receive-material",
  "receiveMaterial": {
    "inventoryLocationId": 123,
    "materialSpecId": 45,
    "itemKind": "FullSheetBundle",
    "quantity": 6,
    "usableWidthIn": 48,
    "usableLengthIn": 120,
    "shapeClassification": "Rectangular",
    "isQuarantined": false,
    "vendorId": 12,
    "purchaseOrderNumber": "PO-1001",
    "receiptNumber": "RCPT-1",
    "vendorPartId": 34,
    "heatLotNumber": "HEAT-1",
    "costPerUnit": 42.50,
    "notes": "Dock 2",
    "purchaseOrderLineId": null
  }
}
```

The result is `{ "inventoryItemId": number, "sheetLotId": number, "publicItemCode": string }`; its `Location` points to `/api/v1/inventory/{inventoryItemId}`.

### `kind: "create-reservation"`

Supply `kind` and exactly one `createReservation` object. `inventoryItemId` is required. If provided, `equipment` must be a valid `ReservationEquipment`, `pepNestYear` must be positive, and each expected remnant needs positive `widthIn` and `lengthIn` plus a valid `sourceType`.

To hold material for an OpenNest.Server nest, send `openNestNestId` (the nest's UUID) and `nestName` (the nest's name, at most 200 characters). `nestName` is required whenever `openNestNestId` is set. `pepNestYear` and `pepNestName` are **deprecated** and will be removed when PEP is retired; a command that sets the OpenNest fields together with either PEP field is rejected. These rules return `400` validation problems keyed by `nestName` or `openNestNestId`.

```json
{
  "kind": "create-reservation",
  "createReservation": {
    "inventoryItemId": 456,
    "shopOpsJobId": "JOB-17",
    "drawingId": "DWG-22",
    "drawingRevision": "C",
    "equipment": "Laser",
    "openNestNestId": "6f9a1c1e-3c55-4d7e-9b0e-2a4f1d2c3b4a",
    "nestName": "NEST-31",
    "laserProgramRecordId": "program-18",
    "expectedRemnants": [
      { "widthIn": 12.5, "lengthIn": 24, "sourceType": "Manual" }
    ]
  }
}
```

The result is `{ "materialReservationId": number, "status": "Proposed" }`; its `Location` points to `/api/v1/reservations/{materialReservationId}`.

Business-rule failures such as invalid inventory availability, purchase-order, location, or reservation state return `409` `domain-conflict`. The API does not duplicate domain mutation logic, and a rejected command does not create partial command state.

## Attachments

Attachment routes use the entity-scoped route values listed in the enum table. The entity must exist before upload. Scoping is enforced on download as well, so an attachment cannot be fetched by guessing only its numeric ID.

### `POST /api/v1/attachments/{entityType}/{entityId}`

Requires `Programmer` or `Manager`. Send `multipart/form-data` with a nonempty `file` part; the API uses the first part named `file`. The configured file limit is **10 MiB** (`10,485,760` bytes). The claimed media type must be one of `application/pdf`, `image/png`, or `image/jpeg`; the filename extension must independently be one of `.pdf`, `.png`, `.jpg`, or `.jpeg`. The application sanitizes the display filename and stores a server-generated name beneath its configured attachment root; it does not execute, preview, or parse uploaded content.

A successful upload returns `201 Created`, a scoped download `Location`, and:

```json
{
  "attachmentId": 12,
  "fileName": "confirmation.pdf",
  "contentType": "application/pdf",
  "byteLength": 12345,
  "checksum": "SHA-256 hexadecimal digest",
  "uploadedAtUtc": "2026-08-12T20:24:37Z",
  "downloadUrl": "/api/v1/attachments/purchase-order/41/12"
}
```

Uploads are not operation-log commands and do **not** accept or provide `Idempotency-Key` semantics in v1. A client may use the immutable attachment ID and SHA-256 checksum to detect that an upload retry completed; exactly-once upload behavior requires a future durable staged-upload design.

### `GET /api/v1/attachments/{entityType}/{entityId}/{attachmentId}`

Requires any authenticated role. Streams the exact stored bytes using the stored safe content type and a safe `Content-Disposition` download filename. A missing attachment, mismatched entity scope, missing file, or unsafe resolved storage path returns `404` and never returns attachment bytes or filesystem path information.

## RFC 9457 problems

Every non-success API response uses `application/problem+json`. Problems use RFC 9457 base members (`type`, `title`, `status`, `detail` when appropriate, and `instance`) and include `traceId`. `type` is an absolute URI under `https://materialledger.local/problems/`. Validation responses can add an `errors` object keyed by camel-case JSON property names.

| Condition | Status | Type URI suffix |
|---|---:|---|
| Missing/malformed JSON, query, route, or idempotency key | 400 | `validation` |
| Missing or invalid API authentication | 401 | `unauthenticated` |
| Authenticated caller lacks route permission | 403 | `forbidden` |
| Idempotency key belongs to another user | 403 | `idempotency-key-ownership` |
| Resource, entity, attachment, or scoped file is absent | 404 | `not-found` |
| Unsupported route method | 405 | `method-not-allowed` |
| Key reused with a different command/payload | 409 | `idempotency-conflict` |
| Domain concurrency conflict | 409 | `concurrency-conflict` |
| Valid request violates domain state/rules | 409 | `domain-conflict` |
| Multipart/file policy size limit exceeded | 413 | `payload-too-large` |
| File media type or extension is disallowed | 415 | `unsupported-media-type` |
| Unhandled server error | 500 | `internal-error` |

Problem details deliberately do not expose exception class names, stack traces, database details, raw operation-log content, attachment `StoragePath`, or other server filesystem details.
