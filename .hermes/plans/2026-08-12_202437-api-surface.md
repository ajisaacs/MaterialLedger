# MaterialLedger API Surface Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Add an authenticated JSON HTTP API for material catalog, inventory, locations, receipt/reservation commands, and attachment transfer while preserving the existing transactional operation-log idempotency semantics.

**Architecture:** Keep domain rules and EF Core access in `MaterialLedger.Data`; add a thin, versioned minimal-API adapter under `MaterialLedger.Web/Api`. Map endpoints below `/api/v1`, use the existing cookie-authenticated principal and role policies, and map API-specific request/response DTOs explicitly rather than serializing EF entities. A single discriminated `POST /api/v1/commands` endpoint dispatches either `receive-material` or `create-reservation` to the existing services; its required `Idempotency-Key` UUID is passed through as the existing `OperationLog.CorrelationId`.

**Tech Stack:** ASP.NET Core 8 minimal APIs, existing cookie authentication/authorization, EF Core 9 and SQL Server, xUnit integration tests with the existing real-SQL fixture.

---

## Scope and contract decisions

1. API root is `/api/v1`; Razor Pages and their routes remain unchanged.
2. Existing cookie authentication is reused. API callers authenticate with the same cookie; unauthenticated API requests return JSON RFC 9457 problems rather than HTML login redirects. No bearer-token mechanism is added in this phase.
3. Read endpoints require any authenticated user. `POST /commands` requires `Programmer` or `Manager`, matching receipt and reservation creation pages. Attachment upload requires the same write role; download requires authenticated access.
4. The one command route is `POST /api/v1/commands`, with a required `kind` discriminator. Supported values in this phase:
   - `receive-material`
   - `create-reservation`
   Adding more commands later does not create more write routes.
5. `Idempotency-Key` is a required request header for `POST /commands`; it must be a UUID/GUID. It is the API spelling of the existing `CorrelationId`, not a second idempotency implementation. The key is scoped by the existing `OperationLogs` primary key, so a reuse with a different command kind or canonical payload returns `409`.
6. Attachment paths are entity-scoped to prevent an attachment from being fetched by guessing only its numeric identifier. API clients upload using entity type plus entity id and download through the same scope:
   - `POST /api/v1/attachments/{entityType}/{entityId}` (`multipart/form-data`, one `file` part)
   - `GET /api/v1/attachments/{entityType}/{entityId}/{attachmentId}`
   `entityType` is limited to the existing `AttachmentEntityType` enum values. Before storing, verify that the referenced entity exists; do not allow orphan attachments.
7. Uploads are not command operations and therefore do not accept `Idempotency-Key` in this phase. The response includes the immutable attachment id and SHA-256 checksum so a client can safely detect a completed retry. If exactly-once upload semantics become necessary, add it as a new operation-log procedure with a durable staged-upload design rather than pretending multipart retries are idempotent.
8. Use camel-case JSON and stable DTOs. Never return EF entities, password hashes, operation-log payloads, server storage paths, or row-version bytes unless a future contract explicitly needs them.

## HTTP contract

### Reads

| Method | Route | Query / result |
|---|---|---|
| `GET` | `/api/v1/materials` | Optional `q`; returns active material specs ordered as `MaterialSpecService.SearchAsync` does. |
| `GET` | `/api/v1/inventory` | Mirrors `InventoryFilter`: `materialFamily`, `grade`, `finish`, `thicknessIn`, `itemKind`, `minUsableWidthIn`, `minUsableLengthIn`, `locationCode`, `availableOnly` (default `true`). Returns canonical `InventoryItemSummary`-derived DTOs. |
| `GET` | `/api/v1/inventory/{id:long}` | Returns the canonical item availability projection; `404` if absent. Include source-sheet summary only for drops, matching the details page. |
| `GET` | `/api/v1/locations` | Returns active locations, ordered by `SortOrder` then location code, with parent id/code, type, storage mode, capacity-confirmed status, and notes. |

```json
  "heatLotNumber": "HEAT-1",

```

```json
{
  "kind": "create-reservation",
  "inventoryItemId": 456,
  "shopOpsJobId": "JOB-17",
  "drawingId": "DWG-22",
  "drawingRevision": "C",

    { "widthIn": 12.5, "lengthIn": 24, "sourceType": "Manual" }
  ]

```

`POST /api/v1/commands` returns `201 Created` for a first successful command and `200 OK` plus `Idempotent-Replay: true` for a successful replay. The body is a stable envelope such as `{ "kind": "receive-material", "result": { ... } }`. It includes `Location` for newly created inventory or reservation resources. This requires the application layer to expose replay metadata without changing `OperationLog` behavior; it must not infer replay by querying for side effects.

### Problem response shape

Every non-success API response uses `application/problem+json` and RFC 9457 base members:

```json
{
  "type": "https://materialledger.local/problems/validation",
  "title": "One or more request values are invalid.",
  "status": 400,
  "detail": "Received quantity must be a whole number of at least 1 sheet.",
  "instance": "/api/v1/commands",
  "traceId": "00-...",
  "errors": { "quantity": ["..."] }
}
```

Use these status/type mappings consistently:

| Condition | Status | Type suffix |
|---|---:|---|
| Missing/malformed JSON, query, route, or `Idempotency-Key` | 400 | `validation` |
| Missing/invalid API authentication | 401 | `unauthenticated` |
| Authenticated but role lacks permission | 403 | `forbidden` |
| Requested inventory/location/attachment/entity is absent | 404 | `not-found` |
| Existing idempotency key used with different command/payload | 409 | `idempotency-conflict` |
| Reservation row-version conflict (future command only) / domain concurrency | 409 | `concurrency-conflict` |
| Valid command that violates inventory/PO/location/reservation rules | 409 | `domain-conflict` |
| Upload exceeds configured size or content policy | 413 or 415 | `payload-too-large` / `unsupported-media-type` |
| Unhandled exception | 500 | `internal-error` |

Do not expose exception class names, stack traces, database details, `StoragePath`, or raw operation-log content in `detail`.

## Risks and guardrails

- The existing test command currently cannot execute the real-SQL integration suite unless `MATERIALLEDGER_TEST_ADMIN_CONNECTION` is set. The current baseline also has an unrelated presentation assertion failure in `CuttingScopeTerminologyTests`; capture the pre-change baseline and do not claim a green full suite until that environment/test issue is resolved.
- `OperationLog.CorrelationId` is globally unique across procedures today. This is intentionally preserved. Do not silently make the idempotency key procedure-scoped without an explicit schema/behavior change.
- Receipt/reservation services currently validate and mutate inside serializable transactions. Endpoint handlers must not reproduce that logic or weaken isolation.
- File and database writes cannot be a single SQL transaction. The storage service must use cleanup and safe-path guards; this phase accepts a small crash-window risk that should be covered later by a reconciliation job if attachment volume grows.
- Do not add OpenAPI/Swagger merely by convention. It is out of the requested basic surface; add it in a later phase only if an interactive/generated client contract is needed.
- Do not expose the API externally or change reverse-proxy/TLS configuration as part of this application-only plan.
